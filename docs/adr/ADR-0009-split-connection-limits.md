# ADR-0009: split the reference host's connection limits

- Status: Proposed. A security review held the first draft on 2026-10-15. This text is that revision. No limit changes until the owner accepts it.
- Date: 2026-10-14
- Revised: 2026-10-15
- Brand: Agent Control Lab
- Licence: Apache-2.0
- Supersedes nothing yet. Amends the limits ADR-0007 set and ADR-0008 recorded.

## Context

ADR-0007 set three limits on the agent socket and ADR-0008 recorded them: an idle timeout of 5 seconds per read (`IDLE_TIMEOUT_SECONDS`), a connection deadline of 30 seconds after accept (`CONNECTION_DEADLINE_SECONDS`), and a cap of 8 connections (`MAX_CONNECTIONS`). A tool call has its own 5 second limit (`TOOL_CALL_TIMEOUT_SECONDS`). ADR-0008 named the consequence: a held session is short, an agent must send a byte at least every 5 seconds, and the operator must grant again after each reconnect.

The owner's decision of 14 October 2026: do not accept 5 seconds idle and 30 seconds deadline as they stand. Split the single limit into separate ones, measure first, then propose numbers with the measurements. This ADR is that proposal. It changes no constant.

The first draft was held. A session bound only by the last grant could live as long as that grant, and the library still accepts a grant TTL up to 86400 seconds. A keep-alive that resets idle with no live grant could hold a slot, and nothing recorded how long the slot was held. The cap of 8 dropped the client that had waited longest without a complete request, so a client that only sent keep-alive lines was not the one removed, and one user id could take every slot. The 10 ms figure could be read as a check that still applies after a tool has started. The 2 second partial-message bound could be read as a timer that starts again on each read. The 90 second idle figure had no trace behind it. The operator range up to 64 connections had no memory or file-handle budget. Those conditions are the decision below.

## Decision proposed

One limit becomes five, and the top of the connection range gains a resource budget. Each has its own name, default, and reason.

1. **Partial-message limit.** Once the first byte of a request line has arrived, the whole line must arrive within 2 seconds or the connection is closed. This deadline is fixed. It starts at that first byte and never restarts on a read. A later byte does not move it. The reference host today arms the socket timeout again on each read, so a byte starts a new wait. This limit must not be armed that way. A completed line ends the deadline. The next unfinished line gets a new 2 second deadline of its own. This is the bound that stops a slow drip.
2. **Idle limit between requests, with keep-alive.** A connection with no request in flight may stay open for this long without bytes. The 90 second figure below is unsupported by data. A keep-alive is an envelope the host answers without a decision and without running a tool. The host counts a keep-alive, and lets it reset the idle timer, only while a live grant exists, and not past the fixed session ceiling. Counting does not continue up to that ceiling when no grant is live. With no live grant, a ping is not counted, does not reset the idle timer, and cannot hold the slot. Once the ceiling has passed, a ping is not counted either. Accepted keep-alives are rate-limited to one per 30 seconds on that connection. A faster repeat does not reset idle and does not get its own log line. The 30 second rate is a proposal and is unsupported by data. It stays its own constant so a later change to the idle figure does not silently change the rate. When a slot is released, the host logs once how long that slot was held, with the close reason and the peer user id.
3. **Session lifetime.** The session ends at whichever comes first of the last grant's expiry, a fixed ceiling of 1 hour after accept, or the idle limit alone when there is no live grant. Keep-alives do not move the grant expiry or the ceiling. A session with no grant cannot hold a slot indefinitely by sending keep-alives. With no live grant, keep-alives do not reset the idle timer, do not stretch the session out to the ceiling, and do not keep the slot open. The idle limit closes it. There is no keep-alive exemption from eviction. Any connection with no request in flight and no live grant is evictable, not only a client that only pings. A client that sends one request and then idles cannot pin a slot. A keep-alive does not protect that connection. The ceiling is always in force, so an idle figure larger than 1 hour still loses to the ceiling. The ceiling uses the host monotonic clock from accept. Grant expiry uses the host clock the grant was minted with. `kill` and (once it exists, L3.7) `revoke` stay instant and are not bounded by this limit. The grant TTL is capped. The host refuses a grant whose TTL is above 3600 seconds, and refuses a grant whose expiry would fall after that connection's ceiling. Today `MAX_TTL_SECONDS` in the approval library is 86400. This ADR does not change that constant. The implementing change caps what the host will mint. It does not raise the session ceiling to 86400.
4. **Gate decision-time budget.** The time the host allows itself to reach a decision, budgeted separately for rules-only decisions (the only kind this host makes) and for any future model-based check (none exists on the decision path; the budget is reserved, not spent). The 10 ms rules-only budget is checked before the request goes to the executor, never after a tool has started. If the budget is already spent at that check, the result is DENY and the executor is not asked. A late decision means the host does not act on a late ALLOW, rather than preemption. The late ALLOW is not handed to the executor, and the tool does not start. A tool that has already started is not stopped by this budget. It keeps the tool-call timeout. A decision that overruns is DENY, logged as such.
5. **Connection cap.** The cap stays 8. It becomes an operator setting with a bounded range of 1 to 64. A per-user sub-cap of 2 applies inside that cap: one attested peer user id may hold at most 2 agent slots. The sub-cap of 2 is a proposal and is unsupported by data. Two slots let that user id reconnect while the previous connection closes, and they cannot take all 8. When the cap is full, the host evicts any connection with no request in flight and no live grant, longest hold first. That is not limited to clients that only ping. A client that sends one request and then idles has no request in flight and no live grant, so it is evictable and cannot pin a slot. Keep-alives are not an exemption from that eviction. The host does not evict a connection that has a request in flight, or a connection that still has a live grant, ahead of one that has neither. If every connection has a request in flight or a live grant, the new connection is refused and nobody is evicted. A user id already at its sub-cap is refused even when the global cap has room. Each eviction is logged once. That line is the slot-release line, with the hold duration and the reason. The close path must not write it twice.
6. **Resource budget at 64 connections.** The operator range may reach 64 only if 64 live agent connections stay inside this budget. In the host process the design holds, per connection, the accepted socket and one worker socket, plus one nursery socket, one spare worker socket, the listener, the log, and the halt file. At 64 connections that is under 200 descriptors. The file-handle budget is 256 open descriptors for that set. It does not count descriptors a test runner inherited into the process. Workers drop inherited descriptors, and the process group of the host plus those workers stays within 512 open file descriptors. The memory budget is 1GiB resident set for that same process group. The file-handle ceilings are the descriptor count plus headroom, not a measured high-water mark. The test records all three (256 counted host file descriptors, 512 file descriptors for the host and its workers, and 1GiB resident set) and fails if any ceiling is exceeded. The 1GiB memory ceiling is unsupported by data until this test records a real resident set. The budget is not raised to match the result without a new owner decision.

## Measurements

`scripts/bench_decisions.py`, run on 14 October 2026 as a non-root user on this machine (Linux 6.18, x86_64, Python 3.13.16), 2000 iterations per series, in-process `handle_request`. Raw output: `docs/benchmarks/2026-10-14-decision-times.json`.

| Series | What it times | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| `deny_unknown_tool` | rules-only DENY with the log append (most lines coalesced by the denial window) | 0.034 ms | 0.074 ms | 0.381 ms | 3.3 ms |
| `deny_envelope_invalid` | rules-only DENY for a malformed envelope | 0.032 ms | 0.065 ms | 0.116 ms | 2.7 ms |
| `allow_echo` | granted `echo.ping` through the executor worker and back | 2.44 ms | 3.63 ms | 5.07 ms | 8.0 ms. Noisy and not reproducible. |

The `allow_echo` max of 8 ms (8.044 ms in the JSON) is noisy and not reproducible. A reviewer re-run gave 22 to 147 ms. That max is not a budget, and it is not evidence for the 10 ms decision check.

The 10 ms decision budget is compared with the rules-only series only. Those samples end before the request would go to the executor. `allow_echo` includes the executor worker and is not the decision budget. The check this budget names happens before that handoff, never after a tool has started. A late decision means the host does not act on a late ALLOW, rather than preemption.

What is not measured: the Unix-socket round trip (the benchmark is in-process; the client and host must be different users, which one process cannot be), the gap between an agent's successive tool calls (this tree holds no agent traces; the script accepts one with `--gaps` and reports the distribution when given), memory at 64 connections, and file handles at 64 connections. The 90 second idle figure is unsupported by data. It rests on the owner's starting range, not on a trace. The 14 October JSON does not record CPU count or load. The script now writes `cpu_count` and `load` (the one, five, and fifteen minute load averages) in every JSON report.

## Tests planned

One test per limit. The implementing change adds these tests. This ADR does not add them.

1. **Partial-message.** Send one byte every 1.9 seconds and never a newline. The connection closes at the 2 second deadline. A byte that arrives before the deadline does not move it. A line that is complete before 2 seconds is accepted, and the next unfinished line gets a new deadline.
2. **Idle and keep-alive.** With no bytes and no grant, the connection closes at the configured idle limit. The test uses that configured value. It does not treat 90 seconds as a measured truth. A keep-alive while a grant is live and the ceiling has not passed resets the idle timer. A second keep-alive before 30 seconds have passed does not reset the idle timer. A keep-alive with no live grant does not reset idle, and a keep-alive after the ceiling does not either. Releasing the slot appends one log line with how long the slot was held.
3. **Session lifetime and grant TTL.** The session ends at whichever comes first of the last grant's expiry, 1 hour after accept, and the idle limit when no grant is live. A session with no grant that sends keep-alives still closes at the idle limit and does not stay open. Those keep-alives are not an exemption from eviction. The host refuses a grant whose TTL is above 3600 seconds, and refuses a grant whose expiry would pass the ceiling. A grant inside the cap does not push the session past the hour.
4. **Decision budget.** The host checks the 10 ms budget before the request goes to the executor. A decision that overruns is DENY, and the tool is not started. A late decision means the host does not act on a late ALLOW, rather than preemption. A tool that has already started is not failed because the call then runs past 10 ms. That case stays on the tool-call timeout.
5. **Connection cap.** When the cap is full, the host evicts a connection with no request in flight and no live grant, longest hold first. The evicted connection may be a client that only pings, or a client that sent one request and then idled. That second client cannot pin the slot. A connection with a request in flight or a live grant is not evicted in its place. If every connection has a request in flight or a live grant, the newcomer is refused and nobody is evicted. The eviction is one log line. Keep-alives do not exempt a grantless idle connection. A third connection from the same user id is refused while the per-user sub-cap is 2, even if the global cap has room.
6. **Resource budget.** The test records all three (256 counted host file descriptors, 512 file descriptors for the host and its workers, and 1GiB resident set) and fails if any ceiling is exceeded. The 1GiB memory ceiling is unsupported by data until this test records a real resident set.

## Consequences

- Each limit gets a constant, a constructor argument, and a README row. The live check gains a row per limit. This is a protocol-visible change for the idle and lifetime limits, so it lands as its own phased change after approval (tests, code, docs, minor version bump per ADR-0003 and ADR-0005 practice).
- A keep-alive envelope is a new request kind. Its shape is decided in the implementing change. The counting rule, the rate limit, and the single slot-hold log line are decided here.
- The partial-message deadline, the session ceiling, the grant TTL cap, the per-user sub-cap, eviction of any connection with no request in flight and no live grant, and the resource budget are part of that same implementing change. They are not applied by this ADR.
- Nothing in this ADR is a claim of efficacy. The decision-time numbers describe one machine on one day. The `allow_echo` max of 8 ms is noisy and not reproducible: a reviewer re-run gave 22 to 147 ms. The 90 second idle figure and the 1GiB memory ceiling are unsupported by data.
